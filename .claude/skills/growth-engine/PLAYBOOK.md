# 1. 플레이북 본문

이 스킬은 SETKORA(`skyrental-toss/`)에서 **실제 트래픽·색인 데이터로 검증되거나, 실제로 깨져서 고친** SEO·마케팅 자동화의 이전 가능한 부분을 담고 있다. 재현 가능한 것만 남겼다 — 잘 될 것 같았지만 측정해보니 아니었던 것도 그대로 적었다.

핵심 전제: **자산은 도구 코드가 아니라 판단 순서와 실패 목록이다.** 도구는 200~2,700줄짜리 스크립트고 하드코딩은 사이트 URL·브랜드명 정도뿐이라 복사가 쉽다. 반면 아래 실패들은 한 번씩 실제로 며칠을 태웠고, 새 세션은 아무 표시가 없으면 전부 다시 밟는다.

### 어떻게 쓰나

작업 성격에 따라 진입점이 다르다.

- **새 프로젝트에 SEO/마케팅을 새로 붙인다** → 아래 "이식 절차"를 따르고, 오프라인 매장(공일모바일)이면 `references/local-seo-offline-store.md`를 반드시 먼저 읽어라. SETKORA 플레이북은 구글 중심 전국 커머스용이고, 매장은 채널 구조 자체가 다르다.
- **이미 사이트가 돌고 있는데 유입이 안 늘어난다** → "성장 병목 사슬"로 단계 진단부터. 코드를 만지기 전에 어느 단계가 0인지 먼저 확정하라.
- **개별 도구를 옮긴다** → `references/port-map.md`에 도구별로 무엇을 바꿔야 하는지 정리돼 있다.
- **정기 운영을 세운다** → `references/routines.md` (일일/주간/월간 런북).
- **왜 이렇게 하는지 근거가 필요하다** → `references/failure-lessons.md` (실패 12건, 각각 무엇이 깨졌고 어떻게 알아챘고 무엇으로 막았는지).

### 성장 병목 사슬 — 이 스킬에서 가장 중요한 한 가지

유입은 사슬이고, **앞 단계가 0이면 뒤 단계 최적화는 전부 낭비다.**

| 단계 | 측정 소스 | 통제 가능? |
|---|---|---|
| ① 크롤 | GSC 크롤 통계 · 서버 로그 | 간접 (사이트맵·내부링크·속도) |
| ② 색인 | GSC 페이지 보고서 · `site:` | 간접 (중복·canonical·품질·**내부링크**) |
| ③ 노출 | GSC 노출수 | 콘텐츠 주제·스키마 |
| ④ 클릭 | GSC 클릭·CTR | title/description |
| ⑤ 방문 | GA4 세션 | 소셜·광고·오프페이지 |
| ⑥ 행동 | GA4 이벤트 | UX·카피 |
| ⑦ 접수 | 텔레그램·D1 | 폼 마찰 |
| ⑧ 성사 | 사장님 회신 | 영업 |

**규칙: 가장 앞에서 0에 가까운 단계 하나만 민다.** 동시에 여러 개 밀지 않는다.

이 규칙은 값비싸게 배웠다. 2026-07-30에 "폼 이탈률 92%가 병목"이라고 진단하고 폼 카피를 고쳤는데, 실제로는 ⑤ 방문 자체가 실제 사람 기준 28일에 10건 미만이었다. 180세션의 대부분이 우리 검증 스크립트와 운영자 본인이었다. **⑦을 고치고 있었는데 ②가 0이었다.** 상품 2,677p 중 2,024p(76%)가 내부링크 고아여서 색인이 아예 안 되고 있었다.

그래서 진단할 때는 **위에서 아래로, 숫자를 실제로 뽑아서** 내려온다. 추측으로 단계를 건너뛰지 않는다.

### 절대 타협하지 않는 6가지

이건 취향이 아니라, 각각 실제 사고에서 나온 것이다. 자세한 사고 경위는 `references/failure-lessons.md`.

1. **검증에 필터를 걸면 그건 검증이 아니다.** 404 체크를 `/\.(js|css)$/`로 필터링해서 상품 이미지 2,677장 404를 "0건"으로 통과시켰다. 사장님이 캡처로 제보해서야 알았다. 실패 요청은 **확장자·경로 구분 없이 전부** 센다.
2. **배포 게이트를 통과해야 배포한다.** 실제 브라우저로 핵심 페이지를 열어 실패요청·깨진 이미지·JS 에러·가로 스크롤·필수 요소·내부링크 수를 검사하고, 위반 시 exit 1. 사람이 눈으로 보는 검증은 반드시 빠진다.
3. **HTML·JS가 뱉는 모든 경로는 루트 절대경로.** 상대경로는 depth 1에서는 잘 돌고 depth 2 URL에서 조용히 전멸한다. 스탬프 단계에서 선행 슬래시를 강제해 두면 누가 다시 상대경로로 써도 자동 교정된다.
4. **모든 페이지는 내부링크 인바운드 ≥1.** 사이트맵에만 있는 페이지는 색인되지 않는다. 관련 항목 추천을 앞에서 `slice(0,N)`으로 자르면 전부 같은 앞 N개만 링크해서 나머지가 고아가 된다 — 반드시 현재 항목 다음 순번부터 회전(rotate)시켜 뽑고, 순환 후속자 한 자리를 고정해 고아 0을 **시뮬레이션으로 증명**하라.
5. **지표에 자동화·내부 접속이 섞이면 결론이 뒤집힌다.** 분석 스크립트를 로드하기 전에 `navigator.webdriver`·헤드리스 UA·내부 opt-out을 걸러라. 단, `bot|spider` 같은 일반어는 쓰지 마라 — CUBOT 같은 실제 단말명에 걸려 진짜 방문자를 지운다.
6. **1회 측정으로 회귀를 단정하지 않는다.** PSI 점수가 45로 나와 34점 회귀로 보고할 뻔했는데 재측정 3회가 99·99·92였다. 성능·순위·CTR은 최소 3회 중앙값.

### 이식 절차

전제: 대상 프로젝트가 이 모노레포 안에 있고, 정적 사이트 + Cloudflare Pages Functions 구조를 따른다(SETKORA와 같은 형태). 다른 스택이면 `references/port-map.md`의 "스택이 다를 때" 절을 본다.

1. **먼저 무엇이 필요한지 줄인다.** 32개 도구를 다 옮기지 마라. 사이트가 아직 없으면 옮길 것도 없다. 페이지가 라이브로 존재하는 순간부터 필요한 순서는 이렇다:
   `build-sitemap` → `stamp-assets` → `deploy-gate` → `seo-check` → `indexnow-ping` → (콘텐츠 시작하면) `build-guides`·`validate-guides`·`build-llms` → (발행 시작하면) `social-topics`·`social-publish`·`youtube`·`gen-post-video`.
2. **사이트 상수를 한 곳으로 뽑는다.** SETKORA 도구들의 하드코딩은 대부분 `const SITE = "https://setkora.com"` 과 브랜드명 문자열이다. 대상 프로젝트에 `tools/site.mjs`(SITE·BRAND·LANGS·HOST) 하나를 만들고 각 도구가 그걸 import 하게 바꾼다. 도구별 정확한 변경 지점은 `references/port-map.md`.
3. **측정 먼저 붙인다.** GA4·GSC·사이트맵 API 제출·UTM·내부 트래픽 제외를 **콘텐츠 발행보다 먼저** 세운다. 측정 없이 발행한 기간의 데이터는 나중에 복구되지 않는다.
4. **배포 게이트를 첫 배포 전에 넣는다.** 나중에 넣으면 이미 깨진 상태가 기준선(baseline)이 되어 게이트가 무력해진다.
5. **첫 4주는 색인 대기 구간으로 잡는다.** 새 도메인은 크롤·색인에 1~3주가 걸린다. 이 구간에 순위·유입을 기준으로 판단하지 마라. 이때 볼 지표는 GSC의 "발견됨/크롤됨/색인됨" 추이 하나다.

### 가드레일 (플라이휠·성장보다 우선한다)

성장 전술보다 이게 먼저다. 어기면 성장이 아니라 사고다.

- **없는 사실을 만들지 않는다** — 가격·후기·승인·계약조건·재고를 지어내지 않는다. 데이터에 없으면 "상담 시 확인" 같은 hedge를 유지한다. 집계로 나온 값만 쓴다.
- **아웃리치는 실제 공개된 주소만** — 이메일 주소를 추측·조합해서 보내지 않는다.
- **커뮤니티 자동 게시 금지** — 게시글 자동 살포는 하지 않는다. 초안까지 만들고 사람이 올린다.
- **시크릿은 저장소 밖** — 토큰·키는 scratchpad에만. 커밋 금지.
- **링크 구매·PBN·스팸 프로필 금지** — 콘텐츠가 링크 자산이다.
- **다국어 프로젝트면 전 언어 동시 패치** — 한 언어만 고치면 나머지가 조용히 영어로 폴백하거나 깨진다. 언어팩 정합성 린터를 fail-closed로 둔다.

# 2. 실패 12건 — 이식 전에 반드시 읽을 것

모두 SETKORA에서 실제로 발생했다. 날짜는 확정된 것만 적었다.
읽는 순서는 상관없지만, **1·2·3번은 이식 작업 시작 전에 반드시** 읽어라 — 새 프로젝트에서 그대로 재발한다.

### 목차
1. 검증 필터가 검증을 무력화 (이미지 2,677장 404)
2. 상대경로가 depth 2 URL에서 전멸
3. 내부링크 고아 76% → 색인 0
4. 지표 오염 — 자동화·본인 접속이 결론을 뒤집음
5. UTM 부재 → 채널 판단 불가
6. 1회 측정으로 회귀 오진 (PSI 45 vs 99)
7. cwd 리셋 → 상위 폴더 배포로 사이트 404
8. `pkill -f` 가 호출한 셸을 죽임
9. 에이전트 프록시가 응답을 중복·404 캐시
10. 코드를 의심하기 전에 데이터를 봐라 (CKOO)
11. 쿼리스트링 URL은 색인 우선순위가 낮다
12. 스크립트 로드 순서에 추적이 흔들림

---

### 1. 검증 필터가 검증을 무력화 — 이미지 2,677장 404

**무슨 일**: 상품 URL을 `/product?id=X` → `/p/X`(depth 2)로 옮긴 뒤 상품 이미지가 전부 404가 됐다. 데이터의 이미지 경로가 `assets/products/….webp`(상대)였고, depth 2에서 `/p/assets/…`로 해석됐다.

**왜 못 잡았나**: 배포 후 검증 스크립트가 404를 세면서 `/\.(js|css)$/`로 필터링했다. 이미지 404가 **집계에 아예 들어오지 않았다.** 검증은 "통과"를 출력했다. 사장님이 스크린샷으로 제보해서 알았다.

**교훈**: 검증에 조건을 붙이는 순간, 그 조건 밖은 검증되지 않는다. "관심 있는 것만 센다"는 최적화가 아니라 눈가리개다.

**방지장치**: `tools/deploy-gate.mjs` — 실제 브라우저로 핵심 페이지를 열고 `status >= 400`을 **확장자·경로 구분 없이 전부** 센다. 추가로 `naturalWidth === 0`인 `<img>`, 잘못 해석된 depth 링크, JS 에러, 가로 스크롤, 페이지별 필수 요소 존재를 검사하고 위반 시 exit 1.

### 2. 상대경로가 depth 2 URL에서 전멸

**무슨 일**: 같은 마이그레이션에서 `product.html`의 상대 `<script src="js/…">`가 `/p/js/…`로 요청돼 스크립트가 전멸했다.

**교훈**: 상대경로는 depth 1에서 정상 동작하므로, URL 구조를 바꾸는 순간까지 문제가 드러나지 않는다. 시간차 지뢰다.

**방지장치**: `tools/stamp-assets.mjs`가 캐시버스트 스탬프를 찍으면서 **선행 슬래시를 강제**한다. 누가 상대경로로 다시 써도 배포 스탬프 단계에서 자동 교정된다. 검증 방법: 일부러 한 파일을 상대경로로 되돌리고 스탬퍼를 돌려 자동 교정되는지 확인했다.

**주의**: og:image와 JSON-LD는 반대로 **절대 URL이 필수**다. 반면 페이지 안의 `<img>`·preload는 상대(또는 루트 절대)여야 한다 — 절대 URL(커스텀 도메인)로 박으면 미러 배포(`*.pages.dev`)에서 크로스오리진이 되어 CSP `img-src 'self'`에 막힌다(실측 확인). 두 용도를 분리해서 변수를 따로 둬라.

### 3. 내부링크 고아 76% → 색인 0

**무슨 일**: GSC에서 상품 페이지 `/p/` 노출이 **0**이었다. 가이드는 정상 색인(32페이지·91노출)이라 사이트 전체 문제가 아니었다.

**원인**: 관련상품 추천이 `[...sameSub, ...sameCat].slice(0, 8)`이었다. 앞에서 자르니 **같은 소분류의 모든 상품이 똑같은 앞 8개만** 링크했다. 나머지는 인바운드 내부링크가 0 — 사이트맵에만 존재했다. 실측 2,677개 중 2,024개(76%)가 고아.

**고친 방법**: 현재 항목 다음 순번부터 고리처럼 회전시켜 뽑고(rotate), **마지막 한 자리는 카테고리 순환 후속자로 고정**한다. 후속자를 고정하는 이유는 소분류 단독 항목(예: sub="FHD" 1개)까지 커버하기 위한 것 — 카테고리 인덱스 +1은 카테고리 전체를 한 바퀴 도는 순열이라 빠지는 항목이 없다.

**중요 — 증명하고 넘어가라**: 처음 회전만 넣었을 때 고아가 26개 남았고, 카테고리 링을 붙여도 25개, 오프셋을 카테고리 인덱스로 바꿔도 1개가 남았다. 전수 시뮬레이션을 돌려 **고아 0 · 인바운드 최소 1 · 중앙값 8 · 최대 14**를 확인하고서야 배포했다. "이론상 될 것 같다"로 넘어가면 안 된다 — 모듈러 산술은 직관이 잘 틀린다.

**서버·클라이언트 양쪽 필요**: 크롤러는 렌더된 DOM으로 링크를 추출하므로, SSR에만 링크를 넣고 클라이언트 렌더가 그 블록을 덮어쓰면 무효가 될 수 있다. **두 곳에 같은 산식**을 넣어라(SSR = JS 미실행 크롤러용, 클라이언트 = 렌더 DOM + 실제 사용자 UX).

**방지장치**: 배포 게이트에 `minProdLinks`(상세 페이지의 다른 항목 아웃링크 최소 개수) 조건.

### 4. 지표 오염 — 자동화·본인 접속이 결론을 뒤집음

**무슨 일**: GA4 28일 180세션을 국가·기기·해상도로 쪼개니 —
- 한국 데스크톱 40세션 / 평균 체류 **691초(11분)** → 운영자·사장님
- 한국 모바일 71세션 / 281초 → 같음
- 미국 55세션 / 평균 체류 **2~9초**, 해상도 1920x10000·2000x2000·800x600 → 우리 Playwright 검증 스크립트와 측정도구·크롤러
- 실제 타깃 방문자로 볼 수 있는 것: **10건 미만**

그런데 이 데이터로 "폼 이탈 92%가 병목"이라고 진단하고 폼 카피를 고쳤다. 분모가 대부분 우리 자신이었으므로 그 결론 자체가 무효였다.

**교훈**: GA4 기본 봇 필터는 IAB 목록만 거른다. 일반 UA를 쓰는 헤드리스 브라우저는 그대로 집계된다. 개발 중 사이트는 **자기 트래픽이 전체의 대부분**이 정상이므로, 필터가 없으면 지표가 아니라 노이즈다.

**고친 방법**: 분석 스크립트 로드 **전에** 차단.
- `navigator.webdriver === true` → Playwright/Selenium 전부
- UA에 `Headless|Lighthouse|PTST|Playwright|Puppeteer` → 측정도구
- `?sk_track=off` → localStorage 플래그로 내부 기기 영구 제외(`?sk_track=on` 해제)

**중요 — 일반어를 쓰지 마라**: `bot|spider|crawl` 같은 단어를 UA 정규식에 넣으면 **CUBOT**(실제 안드로이드 단말 브랜드)에 걸려 진짜 방문자를 지운다. 자칭 크롤러는 대부분 JS를 실행하지 않아 애초에 이 코드에 닿지 않으므로, 자동화 도구 이름만 좁게 잡는 게 맞다.

**중요 — 양면 검증**: "자동화가 차단됐다"만 확인하면 과차단을 놓친다. 3면으로 확인했다.
① 자동화 그대로 → 추적요청 0건 ② `navigator.webdriver` 위장 + **실제 아이폰 사파리 UA** → 2건 정상 전송 ③ `?sk_track=off` → 0건.
②에서 UA를 안 바꿨더니 기본 Playwright UA에 `HeadlessChrome`이 들어 있어 "사람 흉내"가 성립하지 않았고, 처음엔 과차단으로 오판했다.

**남는 한계**: 일반 UA로 JS를 실행하는 크롤러(예: 800x600 Edge)는 이 필터로 안 걸러진다. 국가·체류시간으로 사후 구분하는 수밖에 없다. 한계는 한계로 보고하라.

### 5. UTM 부재 → 채널 판단 불가

**무슨 일**: 발행 파이프라인(소셜·유튜브) 전체에 UTM이 **하나도** 없었다. GA4에서 Direct 121세션 중 98이 홈 랜딩으로 뭉쳐 있었고, 인스타·페북 인앱 브라우저는 리퍼러를 지우는 경우가 많아 소셜 유입이 Direct로 흘러들었다. "어느 채널이 되는지"를 판단할 근거가 없었다.

**고친 방법**: 발행 스크립트가 캡션·설명란의 자사 도메인 링크에 채널별 UTM을 자동 부착한다(`utm_source=instagram|facebook|threads|youtube`, `utm_medium=reels|post|shorts`, `utm_campaign=<경로슬러그>`). 이미 `utm_source=`가 있으면 건드리지 않는다(수동 지정 우선).

**설계 포인트**: 사람이 캡션 쓸 때 UTM을 손으로 붙이게 하면 반드시 빠진다. **도구가 붙여야 한다.** 문서에는 "그냥 맨 URL을 쓰라"고 적어라.

**부수 확인**: UTM이 붙은 URL이 중복 색인되지 않도록 각 페이지에 canonical이 있는지 확인하라.

### 6. 1회 측정으로 회귀 오진

**무슨 일**: PageSpeed Insights 홈 점수가 45로 나왔다(기준선 79). 34점 회귀로 보고할 뻔했다. 재측정 3회가 99·99·92.

**교훈**: 필드가 아닌 랩 측정(PSI/Lighthouse), 검색 순위, CTR은 분산이 크다. **최소 3회 중앙값**으로 판단하고, 1회 측정으로 회귀를 단정하지 않는다. 기준선 파일에 이 규칙 자체를 적어두면 다음 사람이 같은 오진을 안 한다.

### 7. cwd 리셋 → 상위 폴더 배포로 사이트 404

**무슨 일**: 셸 cwd가 수시로 모노레포 상위로 리셋되는데, 그 상태로 `wrangler pages deploy .`를 실행해서 **상위 폴더가 통째로 배포**되어 사이트가 404로 깨졌다.

**방지**: 빌드·배포·git·스탬프 **모든 명령 앞에 프로젝트 디렉터리로 cd**. 배포 절차 문서 맨 앞에 경고로 박아둔다. 도구 안에서는 상대경로 대신 `new URL("..", import.meta.url)` 기준으로 루트를 잡아라.

### 8. `pkill -f` 가 호출한 셸을 죽임

**무슨 일**: `pkill -f "wrangler.*pages dev"` 를 실행했더니 패턴이 호출한 셸의 명령줄 자체에 매칭돼 셸이 죽었다(exit 144). 두 번 반복했다.

**방지**: 프로세스를 띄울 때 PID를 파일에 저장하고 `kill $(cat pidfile)`로 종료한다.

### 9. 에이전트 프록시가 응답을 중복·404 캐시

**무슨 일**: 외부 API 응답이 4번 이어붙어 와서 `JSON.parse`가 깨졌다. 또 신규 배포 별칭·쿼리 URL을 404로 캐시했다.

**대응**:
- JSON은 **첫 균형 객체만 추출**하는 헬퍼를 통해 파싱한다(중괄호 깊이 카운트).
- 외부 API는 node `fetch`가 프록시 환경변수를 무시하므로 **curl**로 호출한다. 프록시 포트는 동적이니 하드코딩 금지.
- 프록시 404는 진짜 404가 아닐 수 있다 — 신규 배포 별칭이나 사용자 브라우저로 **교차검증**한다.

### 10. 코드를 의심하기 전에 데이터를 봐라

**무슨 일**: 상품명이 "CKOO STEAM 100"으로 표시됐다. 브랜드 표시 함수(`dispName()`)의 로마자 변환 버그로 추정하고 코드를 파기 시작했다. 실제로는 **데이터에 `"brand":"CKOO"`가 들어 있었다**(쿠쿠 스크레이핑 오류). 23건.

**교훈**: 표시가 이상하면 렌더 코드보다 **원본 데이터를 먼저** 확인하라. 한 줄 grep이 한 시간을 아낀다.

**부수 교훈**: 정리하면서 `UBUS`도 오염으로 보고 지우려 했는데, 확인해보니 현대렌탈케어의 실제 브랜드(유버스)였다. **오염처럼 보이는 것을 지우기 전에 공식 출처로 확인**하라. 정규화는 되돌리기 어렵다.

### 11. 쿼리스트링 URL은 색인 우선순위가 낮다

**무슨 일**: `?id=` 형태의 상품 URL은 GSC에서 노출이 잡히지 않았다. 구글은 쿼리 파라미터 URL의 크롤 우선순위를 낮춘다.

**대응**: 경로형(`/p/<id>`)으로 일원화하고, 레거시 쿼리 URL은 301 리다이렉트. **리다이렉트 시 `id` 외의 쿼리 파라미터(utm_* 등)는 보존**해야 유입 귀속이 깨지지 않는다. 모르는 id는 200이 아니라 **404**를 반환해야 유령 URL이 색인되지 않는다.

### 12. 스크립트 로드 순서에 추적이 흔들림

**무슨 일**: 폼 단계 이벤트가 한 번도 발화하지 않았다. 폼 스크립트가 추적 스크립트보다 먼저 실행돼서 추적 함수가 `undefined`였다.

**대응**: 공용 유틸에 **큐 시밍**을 둔다 — 추적 함수가 없으면 이벤트를 배열에 쌓아두고, 추적 스크립트가 준비되면 흘려보낸다. 스크립트 순서에 흔들리지 않는다.

**관련**: URL 구조를 바꿀 때 추적 조건식도 같이 바꿔야 한다. `/product`만 보고 있던 정규식이 `/p/<id>` 전환 후 조용히 매칭에 실패해 상품 조회 이벤트가 죽었다. **URL을 바꾸면 URL을 참조하는 모든 곳을 grep**하라 — 추적·사이트맵·리다이렉트·canonical·내부링크.

# 3. 도구 이식표

원본은 `skyrental-toss/tools/`. 하드코딩은 대부분 `const SITE`·`const HOST`·브랜드명 문자열뿐이라 이식 비용이 낮다.
**다 옮기지 마라.** 필요할 때 하나씩 가져가는 게 맞다 — 안 쓰는 도구는 유지보수 부채다.

### 0단계: 사이트 상수를 한 곳으로

대상 프로젝트에 `tools/site.mjs`를 만들고 도구들이 import 하게 바꾼다. SETKORA는 이걸 안 만들고 각 파일에 `const SITE`를 박아둬서 도메인이 바뀌면 8개 파일을 만져야 한다 — 새 프로젝트는 처음부터 뽑아라.

```js
/* 사이트 상수 — 도메인·브랜드가 바뀔 때 여기만 고친다 */
export const SITE = "https://<도메인>";       // 슬래시 없이 끝
export const HOST = "<도메인>";                // IndexNow·필터용
export const BRAND = "<브랜드명>";             // og:site_name·JSON-LD publisher
export const LANGS = ["ko"];                   // 다국어면 확장. 기본언어는 루트 경로
```

### 1단계: 최소 세트 (페이지가 라이브가 되는 순간 필요)

| 도구 | 하는 일 | 바꿀 것 | 비고 |
|---|---|---|---|
| `build-sitemap.mjs` | sitemap.xml(+자식 사이트맵) 생성 | `const BASE` → `SITE`. 페이지 목록·항목 소스를 대상 데이터로 | 항목이 많으면 인덱스+자식 분할 구조 유지 |
| `stamp-assets.mjs` | css/js 참조에 내용해시 `?v=` 부착 + **선행 슬래시 강제** | 파생 빌드 호출부(대상에 없는 빌드는 삭제) | 상대경로 자동교정이 핵심 가치. 절대 빼지 마라 |
| `deploy-gate.mjs` | 실제 브라우저로 핵심 페이지 검사, 위반 시 exit 1 | `PAGES` 배열(경로·필수 셀렉터·최소 내부링크) | **첫 배포 전에** 넣어라. 나중에 넣으면 깨진 상태가 기준선이 된다 |

| `indexnow-ping.mjs` | 검색엔진 즉시 색인 핑 | `HOST`, `ENDPOINT`(자사 릴레이 함수 경로) | 릴레이 함수(`functions/api/indexnow.js`)도 같이 옮겨야 한다 |

**`indexnow-ping` 주의**: Bing 직통은 실행환경에서 막히는 경우가 있어 자사 Cloudflare 함수가 엣지에서 릴레이한다. 2026-07-30 실측에서 **네이버는 3,570 URL 전량 200, Bing은 8배치 전부 429(레이트리밋)**였다 — Bing 429는 정상 범위이고 주간 루틴에서 재핑한다. 한국 타깃이면 네이버 수신이 더 중요하다.

| `social-publish.mjs` | IG·FB·쓰레드 + 스토리 발행, **UTM 자동 부착** | `tagUtm`의 도메인 정규식, 토큰 파일 경로 |
| `youtube.mjs` | 쇼츠 업로드, 설명란 UTM 자동 부착 | 도메인 정규식, OAuth 리다이렉트 URL |
| `gen-blog-image.mjs` | 개념형 주제용 AI 이미지 | 낮 |
| `SOCIAL-FACTORY.md` | 발행 절차 단일 소스 | 문서 전체 재작성 |

**UTM은 도구가 붙인다** — 문서에는 "캡션에 맨 URL을 쓰라"고 적어라. 사람이 손으로 붙이게 하면 반드시 빠진다(실제로 전 채널에서 빠져 있었다).

**자동 발행 불가 채널**: 네이버 블로그는 2020-05 글쓰기 API가 폐지됐다. 네이버 플레이스도 공개 쓰기 API가 없다. 초안 생성까지만 자동화하고 게시는 사람이 한다 — "자동 발행"으로 약속하지 마라.

### 옮기지 말 것

- `build-from-skydump.mjs`, `build-chat-index.mjs`, `build-home-data.mjs`, `build-product-faq.mjs`, `build-collections.mjs`, `gen-collections-i18n*.mjs`, `price-audit.mjs` — SETKORA 렌탈 도메인 전용. 대상 프로젝트의 데이터 모델로 새로 쓰는 게 빠르다.
- `check-display-font.mjs` — SETKORA 디스플레이 폰트 글리프 문제 전용. 같은 폰트를 쓰지 않으면 무의미.

### 스택이 다를 때

이 도구들이 가정하는 것은 딱 두 가지다: **① 정적 HTML 파일이 디스크에 있다 ② 배포 후 공개 URL로 접근 가능하다.** 그 두 조건만 맞으면 프레임워크와 무관하게 동작한다(Next.js·Astro의 빌드 산출물에도 쓸 수 있다).

맞지 않는 경우:
- **HTML이 런타임에만 존재**(완전 SSR·SPA) → `stamp-assets`는 무의미하다. 대신 프레임워크의 자산 해싱을 쓰고, `deploy-gate`·`seo-check`는 그대로 유효하다(라이브 URL만 보므로).
- **호스팅이 Cloudflare Pages가 아니다** → `indexnow` 릴레이 함수를 해당 플랫폼의 서버리스 함수로 옮기거나, 실행환경에서 Bing에 직접 닿는다면 릴레이 없이 호출한다.

### 이식 후 반드시 확인

1. `deploy-gate` 통과 (실패요청·깨진 이미지·JS 에러·가로 스크롤 0, 내부링크 최소치 충족)
2. `seo-check` 통과
3. 라우팅을 바꿨다면 **URL을 참조하는 모든 곳** grep — 추적 스크립트·사이트맵·리다이렉트·canonical·내부링크
4. 내부링크 고아 0을 **시뮬레이션으로 증명** (`failure-lessons.md` 3번 참조)
5. 분석 스크립트에 자동화·내부 트래픽 제외가 들어갔는지, **양면 검증**(자동화 0건 / 실제 UA 정상 집계)

# 4. 정기 운영 런북

SETKORA에서 돌고 있는 루틴의 이전 가능한 형태다. 루틴은 프로젝트 소유이므로 **대상 프로젝트 세션이 자기 루틴을 새로 만든다**(SETKORA 루틴을 공유하지 않는다).

원칙 하나: **통과는 조용히, 실패만 보고.** 정상일 때도 보고하면 사장님이 리포트를 읽지 않게 되고, 그러면 실패 보고도 묻힌다.

### 일일 (자동)

1. **기술 SEO 회귀 감지** — `node tools/seo-check.mjs`. canonical·스키마·robots·사이트맵 규모. 실패 시 보고 + 수리.
2. **핵심 흐름 생존 확인** — 접수/예약 API가 실제로 200을 주는지, 알림 릴레이(텔레그램 등)가 도달하는지. 라이브에서 확인한다(로컬 dev는 DB 바인딩이 없어 의미 없다).
3. **깨진 이미지·404** — 배포가 있었다면 `deploy-gate`가 이미 잡았다. 배포가 없던 날은 생략 가능.

보고 형식: 이상 없으면 침묵. 이상 있으면 **무엇이 / 어디서 / 사용자에게 어떻게 보이는지 / 고쳤는지**.

### 주간 (매주 월)

1. **GSC 추이** — sitemaps API로 submitted/indexed 기록. 신규 도메인 초기에는 **이 숫자 하나가 유일하게 의미 있는 지표**다. 순위·유입으로 판단하지 마라.
2. **쿼리 마이닝** — ① 노출 상위인데 CTR 낮은 쿼리 → 해당 페이지 title/description 개선 후보 ② 사이트에 답이 없는 검색어 → 콘텐츠 백로그에 후보 추가(발행은 승인 흐름 유지).
3. **링크 감사** — `node tools/audit-links.mjs`. 실패 URL은 리포트에 포함.
4. **IndexNow 재핑** — 지난주 429였던 URL.
5. **채널 성과** — UTM 기준으로 채널별 세션·행동. **자동화·내부 트래픽이 제외된 숫자인지 먼저 확인**하고, 아니면 그 사실을 명시하라.
6. **오프페이지 슬롯** — 아웃리치 타깃 1곳 + 맞춤 문안, 블로그용 초안 1편. 링크 구매·PBN·스팸 프로필 금지. 아웃리치는 **실제 공개된 주소만**(추측·조합 금지).
7. **병목 지목** — 리포트 말미에 "이번 주 밀 곳 1개". 여러 개 지목하면 아무것도 안 밀린다.

### 월간 (매월 1일)

1. **콘텐츠 신선도 루프** — 라이브 글 1편을 골라 **실질 업데이트**(새 정보·섹션 추가). 내용 변경 없이 날짜만 갱신하는 것은 스팸 신호이므로 금지 — 갱신할 거리가 없으면 건너뛴다.
2. **데이터 감사** — 가격·재고·연락처 같은 사실 데이터가 현실과 맞는지. 틀린 가격은 신뢰 사고다.
3. **성능 기준선** — PSI 3회 중앙값으로 기록. 1회 측정으로 회귀 단정 금지.

### 플라이휠 프레임 (병목 하나만 민다)

주간 리포트에 6개 바퀴살 표를 채우고 말미에 병목 1개를 지목한다. 성장의 각 요소가 다음을 밀어주는 자기강화 루프이므로, **가장 느린 바퀴살 하나만** 미는 게 전체를 가장 빨리 돌린다.

| 바퀴살 | 지표 | 소스 |
|---|---|---|
| 경험 | 상담→리드 전환, 접수 완료율 | 로그·알림 |
| 트래픽 | 세션·GSC 클릭·광고 CPL | GA4·GSC·광고 |
| 전환 | 주간 접수 → 성사 | 알림·사장님 회신 |
| 재투자 | 주간 광고예산·배율 결정 | 복리 규칙 |
| 추천 | 추천 경유 유입·접수 | DB |
| 콘텐츠 | 라이브 편수·콘텐츠 검색 유입 | GSC |

광고 재투자 복리 규칙(SETKORA): CPL 배율 >1.5면 주 예산 +20~30%(주 50% 급증 금지) · 1.0~1.5 유지 + 시안 교체 · <1.0 중단·진단.

원칙 3개: **병목 우선**(한 곳만) · **경험이 입력, 매출은 출력**(출력을 직접 밀려 하지 않는다 — 할인·과장 금지) · **자동화 기본값**(사람 개입은 승인·컨펌·결제로 최소화).

### 신규 도메인 첫 8주 타임라인

기대치를 미리 맞춰두면 조급한 오판을 막는다.

| 시기 | 볼 것 | 보지 말 것 |
|---|---|---|
| 1~2주 | GSC 등록·사이트맵 제출·크롤 시작 여부 | 순위, 유입 |
| 3~4주 | "발견됨 → 크롤됨 → 색인됨" 전환 추이 | 전환율(방문 자체가 노이즈) |
| 5~6주 | 첫 노출·첫 클릭. 어떤 페이지가 먼저 뜨는지 | 매출 |
| 7~8주 | 노출 상위 쿼리 → 콘텐츠 방향 조정 | — |

이 기간에 색인이 전혀 진행되지 않으면 **내부링크와 사이트맵을 먼저 의심**하라(콘텐츠 품질보다 앞선다). 색인 0의 가장 흔한 원인은 링크 고아다.

# 5. 오프라인 매장 고유 영역 — 공일모바일에서 가장 중요

대상: 공일모바일(`gongil-mobile/`) 같은 **단일 오프라인 매장 + 방문 예약** 모델.
사업 배경·확정 결정·규제 가드레일은 `gongil-mobile/KICKOFF.md`가 단일 소스다 — 이 문서는 그 위에 얹는 **SEO·마케팅 채널 구조의 차이**만 다룬다.

### 먼저: 무엇이 다른가

SETKORA는 전국 커머스 + 구글 중심 + 다국어 롱테일(상품 2,677p)이다. 매장은 세 축이 전부 다르다.

| | SETKORA | 오프라인 매장 |
|---|---|---|
| 주 검색면 | 구글 (+네이버) | **네이버 플레이스·지도가 1순위**, 구글은 보조 |
| 승부처 | 롱테일 상품 페이지 대량 색인 | **지역 의도 쿼리 + 상담형 콘텐츠** |
| 전환 | 온라인 접수 | 방문 예약 → 내점 → 대면 성사 |
| 자동화 여지 | 높음 (사이트맵·IndexNow·발행 전부 API) | **낮음** — 핵심 채널에 쓰기 API가 없다 |

**가장 중요한 경고**: 매장 사업에서 유입의 큰 몫은 네이버 플레이스/지도와 네이버 블로그·카페에서 나오는데, **이 채널들은 공개 쓰기 API가 없다.** 네이버 블로그 글쓰기 API는 2020-05 폐지됐고, 스마트플레이스는 웹 콘솔 운영이다. 즉 SETKORA식 "발행까지 전자동"이 성립하지 않는다.

그래서 여기서 자동화의 역할은 **발행이 아니라 준비와 감시**다:
- 초안·문안·이미지·영상 생성 → 자동
- 게시·플레이스 정보 갱신·리뷰 응대 → 사람(사장님)
- 순위·노출·유입 추적과 회귀 감지 → 자동

이걸 처음부터 명확히 하라. "자동으로 올려드립니다"라고 약속하면 지킬 수 없다.

### 승부처: 어떤 쿼리를 노리나

**피할 것 — 정면 승부가 안 되는 쿼리**
- 기기명 단독("아이폰 17 프로") — 제조사·통신사·대형 유통사가 점유. 단일 매장이 이길 수 없다.
- 전국 단위 "휴대폰 성지" 류 — 경쟁 극심하고, 과장 광고 규제와 충돌 위험이 크다.

**노릴 것 — 이길 수 있는 쿼리**
1. **지역 + 거래 의도** — "<지역명> 휴대폰 개통", "<지역명> 번호이동", "<지역명> 중고폰 매입". 플레이스 최적화 + 지역 언급이 자연스러운 콘텐츠로 잡는다.
2. **상담형·비교형** — "번호이동 기변 뭐가 유리", "알뜰폰 갈아타기 절차", "자급제 + 요금제 조합 계산". 검색자가 결정을 못 한 상태이므로 방문 예약으로 연결하기 쉽다. 콘텐츠 자산으로 남는다.
3. ⭐ **외국인 + 개통/유심** — 이게 저평가된 기회다. 아래 별도 절.

### ⭐ 외국인 세그먼트 — 가장 경쟁이 적고, 우리만 가진 무기

한국 거주 외국인의 휴대폰·유심 개통은 실제 수요가 크지만, 경쟁 매장은 거의 전부 한국어 전용이다. 반면 이 모노레포에는 **SETKORA의 13개 언어 파이프라인과 이미 색인된 SIM 가이드**가 있다.

- SETKORA의 SIM/휴대폰 가이드는 이미 다국어로 색인돼 있다(GSC에서 다국어 가이드 노출 확인됨) → 여기서 매장으로 링크하면 **처음부터 유입이 있는 상태로 시작**할 수 있다. 새 도메인의 1~3주 색인 공백을 건너뛰는 유일한 경로다.
- 외국인 검색은 구글·구글지도 비중이 한국인보다 훨씬 높다 → 네이버 플레이스에 의존하지 않는 유입원이 생긴다. 채널 분산 효과.
- 다국어 페이지는 SETKORA의 번역·검증 파이프라인을 그대로 재사용할 수 있다(`port-map.md` 2단계).

**순서 제안**: 한국어 로컬(플레이스+지역 쿼리)로 기반을 잡고, **외국인 다국어를 두 번째 축**으로 붙인다. 세 번째가 상담형 콘텐츠. 세 개를 동시에 시작하지 마라 — 병목 하나만 민다.

### 기술 SEO — 매장에서 추가로 필요한 것

SETKORA에 없던 부분이다.

1. **LocalBusiness 구조화 데이터** — `LocalBusiness`(또는 하위 타입)에 `name`·`address`(PostalAddress)·`geo`·`telephone`·`openingHoursSpecification`·`priceRange`·`sameAs`(플레이스·SNS URL)를 넣는다. **사업자등록상 정보와 글자 그대로 일치**시켜라 — 플레이스·사이트·푸터의 상호·주소·전화번호가 다르면 신뢰 신호가 깨진다(NAP 일관성).
2. **예약 페이지** — 방문 예약이 전환 목표이므로 예약 페이지가 색인 가능해야 하고, 날짜·시간·희망 기기를 받는다. 개인정보(신분증·본인확인)는 **온라인에서 받지 않는다** — 방문 예약 모델을 택한 이유가 그것이다(`KICKOFF.md`).
3. **영업시간·임시휴무** — 구조화 데이터와 플레이스 양쪽. 틀린 영업시간은 헛걸음을 만들고 리뷰로 돌아온다.
4. **길찾기·주차·층수** — 매장 페이지의 실질 콘텐츠이자 실제로 많이 찾는 정보다.

### 규제 가드레일 (성장 전술보다 우선)

`KICKOFF.md`에 정리된 원칙을 그대로 따른다. 요지:

- **가격은 항상 "예상 월 납부액 범위 + 최종가는 매장 확정"** 구조. 확정가·최저가 단정 금지. 단통법 폐지(2025.7, `KICKOFF.md` 기재) 이후에도 **허위·과장 지원금 광고 규제는 존속**한다.
- **중고 매입가도 "모델·상태 기준 예상 범위"**로만.
- 시세가 일 단위로 변동하므로, 숫자는 코드에 박지 말고 **관리자 페이지에서 사장님이 갱신**하는 구조로 설계한다. 사이트 카피에 가격을 하드코딩하면 매일 거짓말이 된다.
- 지원금·정책 관련 문구는 자동 생성에 맡기지 마라. 승인된 표현을 재사용만 한다.

### 측정 — 매장 특유의 함정

- **전환은 온라인에서 끝나지 않는다.** 예약 → 내점 → 성사 사이에 이탈이 있고, 온라인 지표로는 안 보인다. 예약 건수만 보고 최적화하면 "예약만 하고 안 오는" 유입을 늘리게 된다. **내점·성사 수는 사장님 회신으로 주간 집계**해서 예약 대비 비율을 같이 본다.
- **전화 문의가 주 전환 경로일 수 있다.** 매장 사업에서 흔하다. 전화번호 클릭(`tel:`)을 이벤트로 잡아라 — 안 잡으면 가장 큰 전환 채널이 지표에서 통째로 빠진다.
- **지표 오염은 매장에서 더 심하다.** 사장님이 자기 매장 페이지를 하루에도 여러 번 열어본다. `?sk_track=off` 내부 제외를 **첫 배포 때부터** 넣어라(`failure-lessons.md` 4번).
- **플레이스 유입은 GA4에서 리퍼러가 불완전**하다. 플레이스에 등록하는 홈페이지 URL에 UTM을 붙여두면 구분이 된다.

### 확실하지 않은 것 — 단정하지 말 것

- 네이버 플레이스의 순위 결정 요소는 공개돼 있지 않다. "이렇게 하면 상위 노출" 식으로 사장님께 약속하지 마라. 할 수 있는 것은 정보 완전성·NAP 일관성·리뷰 응대·콘텐츠 축적 같은 **일반적으로 인정되는 기본기**를 갖추고, 결과를 측정하는 것이다.
- 리뷰는 절대 조작하지 않는다(가짜 후기 금지는 이 저장소 공통 가드레일). 실제 고객에게 요청하는 것까지가 선이다.
- 특정 커뮤니티·카페 자동 게시는 금지다. 초안까지만.

# 6. 부록: GA4·GSC 조회 스크립트 전문

저장소 경로: `.claude/skills/growth-engine/scripts/google-api.mjs`

이 스크립트를 저장소에 넣어둔 이유: 원래 세션 전용 임시폴더(scratchpad)에 있었는데 **새 세션에서는 사라진다.**
그러면 다음 세션이 토큰 발급부터 다시 쓰게 되고, 네 가지 함정(토큰 1시간 만료 / node fetch 가 프록시를 안 탐 /
프록시가 응답을 중복 전송 / GSC 사이트 식별자 추측 시 403)을 전부 다시 밟는다.

실측 검증 완료 — `gsc-sites`·`gsc-pages`·`ga4-report` 3개 명령 모두 라이브 응답 확인.

```js
/* 구글 API(GA4 Data · Search Console) 호출 헬퍼 — 서비스 계정 JSON 하나로 토큰 발급부터 조회까지.

   왜 저장소에 있나: 이 로직은 매 세션 다시 쓰게 되는데, 세 가지 함정이 있어서 처음 쓰면 반드시 막힌다.
     ① 액세스 토큰은 약 1시간 만료 → 세션 중간에 조용히 401이 난다. 매 호출마다 새로 받는다.
     ② node fetch 는 프록시 환경변수를 안 타서 에이전트 환경에서 막힌다 → curl 로 호출한다.
        프록시 포트는 동적이므로 절대 하드코딩하지 않는다(curl 이 환경변수를 알아서 쓴다).
     ③ 에이전트 프록시가 응답을 여러 번 이어붙여 보내는 버그가 있어 JSON.parse 가 깨진다
        → 첫 균형 객체만 잘라서 파싱한다.
   ④ GSC 사이트 식별자는 추측하면 403 이 난다. sites 를 먼저 조회해서 실제 값을 쓴다
      (도메인 속성은 sc-domain:example.com, URL 접두어 속성은 https://example.com/ 로 서로 다르다).

   사용:
     node google-api.mjs <서비스계정.json> gsc-sites
     node google-api.mjs <서비스계정.json> gsc-pages <siteUrl> [시작일 종료일]
     node google-api.mjs <서비스계정.json> ga4-report <propertyId> <디멘션,디멘션> [지표,지표] [시작 종료]

   예:
     node google-api.mjs sa.json gsc-pages "https://example.com/" 2026-07-01 2026-07-30
     node google-api.mjs sa.json ga4-report 546150728 landingPage sessions,activeUsers 28daysAgo today

   서비스 계정에 각 콘솔에서 권한을 먼저 부여해야 한다(GA4: 속성 뷰어, GSC: 사이트 사용자). */
import { readFileSync } from "node:fs";
import { createSign } from "node:crypto";
import { execFileSync } from "node:child_process";

const SCOPES = {
  ga4: "https://www.googleapis.com/auth/analytics.readonly",
  gsc: "https://www.googleapis.com/auth/webmasters.readonly",
};

/* 프록시가 응답을 중복 전송해도 첫 객체만 취한다 — 중괄호 깊이로 균형점을 찾는다 */
export function parseFirstJson(text) {
  const start = text.indexOf("{");
  if (start < 0) throw new Error("JSON 응답이 아니다: " + text.slice(0, 200));
  let depth = 0;
  for (let i = start; i < text.length; i++) {
    if (text[i] === "{") depth++;
    else if (text[i] === "}" && --depth === 0) return JSON.parse(text.slice(start, i + 1));
  }
  throw new Error("JSON 이 잘려서 왔다: " + text.slice(0, 200));
}

const curl = (args) => execFileSync("curl", ["-sS", "--max-time", "60", ...args], { encoding: "utf8", maxBuffer: 64e6 });

/* 서비스 계정 → 액세스 토큰. 만료가 1시간이라 캐시하지 않고 필요할 때마다 받는다 */
export function accessToken(saPath, scopeKey) {
  const key = JSON.parse(readFileSync(saPath, "utf8"));
  const now = Math.floor(Date.now() / 1000);
  const b64 = (o) => Buffer.from(JSON.stringify(o)).toString("base64url");
  const input = b64({ alg: "RS256", typ: "JWT" }) + "." +
    b64({ iss: key.client_email, scope: SCOPES[scopeKey], aud: key.token_uri, iat: now, exp: now + 3600 });
  const jwt = input + "." + createSign("RSA-SHA256").update(input).sign(key.private_key).toString("base64url");
  const out = parseFirstJson(curl([
    "-X", "POST", key.token_uri,
    "-d", "grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer",
    "--data-urlencode", "assertion=" + jwt,
  ]));
  if (!out.access_token) throw new Error("토큰 교환 실패: " + JSON.stringify(out).slice(0, 300));
  return out.access_token;
}

const api = (url, token, body) => {
  const res = parseFirstJson(curl(body
    ? ["-X", "POST", url, "-H", "Authorization: Bearer " + token, "-H", "Content-Type: application/json", "-d", JSON.stringify(body)]
    : [url, "-H", "Authorization: Bearer " + token]));
  if (res.error) throw new Error(`API 오류 ${res.error.code}: ${res.error.message}`);
  return res;
};

export const gscSites = (sa) =>
  api("https://searchconsole.googleapis.com/webmasters/v3/sites", accessToken(sa, "gsc")).siteEntry || [];

export const gscQuery = (sa, siteUrl, body) =>
  api(`https://searchconsole.googleapis.com/webmasters/v3/sites/${encodeURIComponent(siteUrl)}/searchAnalytics/query`,
    accessToken(sa, "gsc"), body);

export const ga4Report = (sa, propertyId, body) =>
  api(`https://analyticsdata.googleapis.com/v1beta/properties/${propertyId}:runReport`, accessToken(sa, "ga4"), body);

/* ── CLI ────────────────────────────────────────────────────────────────── */
if (import.meta.url === `file://${process.argv[1]}`) {
  const [sa, cmd, ...rest] = process.argv.slice(2);
  if (!sa || !cmd) {
    console.error("사용: node google-api.mjs <서비스계정.json> <gsc-sites|gsc-pages|ga4-report> [인자...]");
    process.exit(1);
  }
  const pad = (v, n) => String(v).padStart(n);

  if (cmd === "gsc-sites") {
    for (const s of gscSites(sa)) console.log(`${s.permissionLevel.padEnd(16)} ${s.siteUrl}`);

  } else if (cmd === "gsc-pages") {
    const [siteUrl, startDate = "28daysAgo", endDate = "today"] = rest;
    if (!siteUrl) throw new Error("siteUrl 필요 — 먼저 gsc-sites 로 정확한 값을 확인하라");
    /* GSC 는 상대 날짜를 안 받는다 — 숫자 일수로 환산한다 */
    const iso = (d) => d.toISOString().slice(0, 10);
    const rel = (s) => {
      const m = /^(\d+)daysAgo$/.exec(s);
      if (s === "today") return iso(new Date());
      if (m) return iso(new Date(Date.now() - Number(m[1]) * 864e5));
      return s;
    };
    const r = gscQuery(sa, siteUrl, { startDate: rel(startDate), endDate: rel(endDate), dimensions: ["page"], rowLimit: 100 });
    const rows = r.rows || [];
    for (const x of rows) console.log(`${pad(x.impressions, 6)}노출 ${pad(x.clicks, 4)}클릭  ${x.keys[0]}`);
    console.log(`\n페이지 ${rows.length}개 · 총노출 ${rows.reduce((a, x) => a + x.impressions, 0)} · 총클릭 ${rows.reduce((a, x) => a + x.clicks, 0)}`);
    if (!rows.length) console.log("노출 0 — 색인이 안 됐을 가능성. 내부링크 고아와 사이트맵을 먼저 의심하라(failure-lessons.md 3번).");

  } else if (cmd === "ga4-report") {
    const [propertyId, dims, mets = "sessions", startDate = "28daysAgo", endDate = "today"] = rest;
    if (!propertyId || !dims) throw new Error("사용: ga4-report <propertyId> <디멘션,…> [지표,…] [시작 종료]");
    const r = ga4Report(sa, propertyId, {
      dateRanges: [{ startDate, endDate }],
      dimensions: dims.split(",").map((name) => ({ name })),
      metrics: mets.split(",").map((name) => ({ name })),
      orderBys: [{ metric: { metricName: mets.split(",")[0] }, desc: true }],
      limit: 100,
    });
    for (const x of r.rows || []) console.log(x.metricValues.map((m) => pad(m.value, 7)).join(" ") + "  " + x.dimensionValues.map((d) => d.value).join(" / "));
    console.log(`\n행 ${(r.rows || []).length}개  (지표 순서: ${mets})`);
    console.log("※ 자동화·본인 접속이 제외된 숫자인지 확인하라 — 아니면 결론이 뒤집힌다(failure-lessons.md 4번).");

  } else {
    throw new Error("알 수 없는 명령: " + cmd);
  }
}
```
